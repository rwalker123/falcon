The prototypeClick a knowledge twice

Three things to try. Click the same knowledge twice — it opens, then closes, and the row returns to its line. Click a heading — the whole subject area folds to one line that still says what is inside it. Switch the filter — subject areas with no match fold themselves, and unfold when you go back to All.

Note 1A second click closes it

The last prototype treated a click as select, so there was no way back to a plain list — which is worse here than it was in a columns layout, because an open detail pushes every row under it down the panel. The rule now:

  • Click an open knowledge → it closes. Nothing is selected; the panel is a plain list again.
  • Click a different one → the open one closes and the new one opens. Only ever one open, so the panel's height stays predictable and there is no "close all" to hunt for.
  • Escape closes it, and there is a ✕ in the detail's corner for the same job.

The one-at-a-time rule matters more than it looks. Letting several stand open turns the screen into an accordion whose height is a function of how much the player has poked at it, and the panel is centred in its room — so it would grow in both directions from the middle of the screen every time a row was opened.

And the card must not resize as rows open. A detail is wider than a bare ladder row, so a card fitted to its content narrows when the detail closes and widens when it opens — on a centred panel that is a visible lurch on every click. In AutoSizingPanel terms the row layout wants target_width to be the panel's actual width rather than the nominal floor it is today, so fit_width has nothing left to fit. The same goes for height: fit it to the tallest state, or the card grows and shrinks vertically too.

This changes what the shipped payload means, not just the renderer. KnowledgePanel's PAYLOAD_SELECTED is a knowledge key and the empty string already means "nothing selected" — the detail pane renders its placeholder for it — so a toggle is set the key, or set it back to empty, with no new state. What does need care is the orb hand-over: the turn orb's knowledge rows open this screen on a filter and a key, so opening from outside must always open, never toggle a row shut because the player happened to have it open already.

Note 2Subject areas, and where they come from

Your instinct is right, and it buys more than tidiness: it puts a bound on the thing that grows. Domains grow without limit; subject areas do not, because they answer "what part of the game is this" and that list is short and stable. Six areas holding twenty-four domains reads; twenty-four bare rows do not.

Here is the taxonomy the prototype uses. It follows your steer — Land and Herds are one thing, Roads is the start of infrastructure, and Craft is the start of industry rather than a peer of the food webs.

Note what that does today: six domains become three areas, because an area with no branches is never drawn — the same rule that already forbids an empty column, one level up. So this is not a change that only pays off later; it shortens the current screen too.

The area has to come off the config, not out of a client table

This is the part worth being strict about, because the panel has been here before. LADDER_DOMAINS was a hard-coded client list, and it is why the route branch's Roadbuilding and Paving had nowhere to appear — the fix was to make the sim publish a roster and let the panel build itself from it. A hard-coded area table would reintroduce exactly that bug one level up: the first branch somebody adds without editing the client would fall out of the screen.

The branches themselves have no record in intensification_ladder.json today — branch is just a string repeated on each rung. So the change is to give them one: 

"branches": {
  "plant":      { "area": "food" },
  "animal":     { "area": "food" },
  "forestry":   { "area": "making" },
  "extraction": { "area": "making" },
  "route":      { "area": "works" }
},
"areas": ["food", "making", "works", "reach", "lore", "war"]

areas is the display order — the areas are peers, so first-seen order off the rungs would reshuffle the screen whenever a rung was added. Each ladder_knowledge roster row then carries its area beside the branch, order and is_step it already carries, and KnowledgeRoster groups domains into areas the way it groups nodes into domains now. The craft fan is not a ladder branch, so its area is named where its nodes are built.

Two fallbacks, both load-bearing. A branch whose descriptor names no area, or names one the client has no word for, must still draw — under its own capitalized token, the way HudKnowledgeVocab.domain_label already handles an unknown branch. A knowledge that vanishes because a config edit was incomplete is the worst possible failure for this screen, and it is the failure it has actually shipped once.

The labels stay client-side copy, exactly as the branch labels do now — the wire says food and a player reads Food, and that table lives beside DOMAIN_BRANCH_LABELS in HudKnowledgeVocab where the localization pass can reach it.

Note 3Folding, without hiding

A heading folds on click. The part that needs stating plainly, because it looks like a rule the panel already has: a folded area is not a hidden one. The shipped rule is that a track at 0.0 is drawn greyed rather than skipped, and that the filters dim rather than remove — both exist because a new player who has learned nothing must still be shown there is something to learn.

A folded heading keeps that promise: it stays on screen, and it says what is inside it — "3 to learn", "2 learning · 1 unused". The player is told the area exists and what state it is in; they are one click from the detail. That is different in kind from the old _build_knowledge_block skip, which drew nothing at all.

So the defaults follow from that distinction:

  • Everything starts open. Never fold an area because it is empty of progress — that is the old bug wearing a caret.
  • A filter folds the areas it does not match, and unfolds them on the way back to All. Under All the dim-don't-hide rule is untouched; under a filter, folding is what makes the filter useful at twenty-four domains instead of leaving the player to scroll past dimmed rows.
  • A fold the player made by hand outlives a filter change, and is forgotten when the screen closes. There is no persisted UI state here and this does not need to invent any.
